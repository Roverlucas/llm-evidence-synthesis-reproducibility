\begin{abstract}
Environmental evidence bases are increasingly assembled with large language models, on the assumption that identical inputs yield identical outputs. We test that assumption with an open audit harness on a screening-and-extraction pipeline over 500 abstracts on fine particulate matter and respiratory health: six deployment stacks, ten runs each (35{,}636 of 36{,}000 calls). Local stacks reproduced exactly (Exact Match Rate 1.000); API-served stacks reached 0.150--0.470 on extraction at temperature zero, the most reproducible accepting no seed. The same LLaMA model was deterministic locally but varied across runs when served in the cloud. Neither a fixed-slot prompt nor a decision model returning probabilities removed the variation. Schema conformance was independent of reproducibility (local extraction: 38--43\%). A client that logged temperature zero while omitting it shows that provenance must record the transmitted payload. Harness, run cards and human labels ($\kappa{=}0.529$) are released.
\end{abstract}

\textbf{What the harness does:} it runs a task $R$ times against each configured endpoint through one runner interface (Ollama,
Anthropic, Google and OpenAI clients; the same-checkpoint cloud, decision-model and fixed-slot arms use separate
scripts), and emits a call record per request (for the six main stacks, a hash of the declared configuration

estimates---the propagation of run-to-run variation into a pooled meta-analytic result. Corpus, prompts
and schemas are files; adding a stack means one entry in the model table of \texttt{run\_experiment.py}
and, for a new provider, one runner module. Every result reported here was obtained on one environmental
evidence task, PM$_{2.5}$ and respiratory health, and is scoped to it.

\section{Introduction}

\subsection{Evidence Pipelines Are Becoming Software}

Environmental evidence bases are increasingly assembled by software rather than by hand. Regulatory reviews, exposure assessments and air-quality standards rest on syntheses of primary literature, and the screening and extraction steps that produce them are now routinely delegated to large language models. Work in this journal has begun mapping that shift, scaling open-weight models for regulatory information extraction in the hydropower domain \citep{yoon2026hydropower} and examining what structured tool interfaces do and do not provide for LLM-driven model calibration \citep{park2026toolinterfaces}.

That first study also illustrates the assumption this paper sets out to test, and it does so in the way the field as a whole does. Its experimental setup fixes temperature at zero \emph{``thereby eliminating sampling variability and facilitating consistent outputs across multiple experimental runs''}, and executes each model--method permutation once \citep{yoon2026hydropower}. That is the conventional move: a single execution is treated as sufficient because the decoding parameters are believed to make repetition redundant. The premise is stated openly there, which is what allows it to be tested here; our question is not whether that study was well conducted but whether the premise it shares with the field survives measurement.

Delegating a pipeline step to an LLM makes that step a piece of software, and model and software evaluation is part of this journal's stated scope. Yet the procedure being introduced here carries a property that conventional environmental software does not. A hydrological model run twice on the same inputs returns the same outputs; an LLM endpoint offers no such guarantee, and whether it happens to behave deterministically is a property of how it is served, not of the model named in the methods section. Recent work in this journal has confronted the reproducibility of geoscientific analysis pipelines directly, distinguishing methodological, results and inferential reproducibility, and cataloguing the barriers to each \citep{schlogl2026reproducibility}. That catalogue already names the problem we quantify: it lists ``non-deterministic model outputs from generative AI'' among the barriers to computational reproducibility, and observes that the adoption of large language models introduces reproducibility challenges of a new kind. It does not measure them, and it is not a study designed to. This paper supplies the measurement for one such component, in the dimension that catalogue calls methodological reproducibility---the exact repetition of a procedure given the same code, data and environment.

Evidence synthesis---screening the literature, extracting effect estimates and pooling them---underpins environmental standards and exposure assessments \citep{higgins2019cochrane,page2021prisma}, and its screening and extraction steps are among the most labour-intensive parts of the work \citep{borah2017analysis}.
LLMs now perform those steps with accuracy approaching that of human reviewers \citep{oami2024screening,gartlehner2024extraction,jensen2025chatgpt}, and LLM-assisted synthesis is an established methodological line \citep{li2025jamia,scherbakov2025jamia,matsui2024screening,oami2025optimal}.
Those evaluations report accuracy from one or two runs; whether a second run returns the same output is what this paper measures.
Reporting guidance is beginning to catch up: a 2025 editorial in \emph{Research Synthesis Methods} \citep{farotimi2025rsm_genai_guidance} asks authors of GenAI-assisted syntheses to document random-seed values and, for commercial models, API versions and access dates. What such guidance does not yet establish---and what an audit must supply---is whether documenting those settings buys the determinism their presence implies.

\subsection{The Hidden Problem: Non-Determinism}

Behind this guidance sits an assumption: \emph{if you ask the same question twice, you should get the same answer}.
In the context of LLM-assisted evidence synthesis, this means that running the same model with the same prompt, temperature, and random seed on the same abstract should produce identical screening decisions and extraction outputs every time.

This assumption does not hold in practice.

\citet{atil2024nondeterminism} showed accuracy variations of up to 15\% across repeated identical runs, with best-to-worst performance gaps reaching 70\%.
\citet{klishevich2025codereview} confirmed that temperature${=}$0 does not guarantee deterministic outputs across any of the major models tested (GPT-4o, Claude~3.5, LLaMA~3.2).
At a deeper level, \citet{fu2026beyond} demonstrated that even when surface-level text appears identical, the underlying token probability distributions exhibit substantial instability, suggesting that apparent determinism may mask hidden variation.
A philosophical analysis by \citet{karelin2024indeterminism} traced this non-determinism to three fundamental sources: numerical precision in floating-point operations, architectural choices in distributed inference, and sampling procedures inherent to the generation process.

\subsection{Why This Matters for Evidence Synthesis}

In evidence synthesis, run-to-run variation enters the result at three points.

\textbf{First, decisions propagate.}
A screening decision that flips from ``include'' to ``exclude'' in a repeated run does not merely change one data point---it removes an entire study from downstream analysis.
In meta-analysis, where pooled effect estimates are sensitive to study composition, a single inclusion change can shift a confidence interval across the null, transforming a statistically significant finding into a non-significant one.

\textbf{Second, extraction compounds variation.}
Data extraction involves free-text parsing of complex scientific results---relative risks, confidence intervals, exposure definitions, population characteristics.
Even small variations in how an LLM parses ``RR${=}$1.05 (95\% CI: 1.01--1.09)'' can propagate through meta-analytic pooling.
\citet{gartlehner2024extraction} replicated a Claude~2 extraction twice and reported 96.9\% and 95.0\% accuracy against human extraction; each replication was scored against the reference, not against the other, so the design does not measure how many values change between runs.

\textbf{Third, a review that cannot be re-executed cannot be audited.}
The broader reproducibility crisis in AI research \citep{hutson2018science,haibe2020nature,kapoor2023leakage} has already eroded trust in computational findings.
When LLM-assisted reviews cannot be independently reproduced because the API returns different outputs, the scientific value of those reviews is undermined \citep{han2025biomedical,desai2025reproducibility,semmelrock2025barriers}.

\subsection{The Gap We Address}

Despite the rapid adoption of LLMs in evidence synthesis, \textbf{no study has measured the run-to-run reproducibility of both screening and extraction, and the survival of extraction variation into a pooled estimate}, in an environmental evidence task.

Consider the state of current evidence.
\citet{jensen2025chatgpt} report 94.1\% inter-session reproducibility for ChatGPT-4o extraction---an encouraging number.
But this was measured with only 2~repetitions and evaluated per-field, not per-output.
As we demonstrate below, applying a stricter whole-output metric across 10~repetitions yields extraction EMR as low as 15.0\%; because metric, run count, model and corpus also differ from that study, the two figures are not a like-for-like contrast.
Similarly, \citet{gartlehner2024extraction} report replication accuracies of 95.0--96.9\% against human extraction over two replications, which does not measure how many values change between runs.
Studies measuring non-determinism \citep{atil2024nondeterminism,klishevich2025codereview} do so on general NLP benchmarks, where the structured, multi-field outputs characteristic of evidence synthesis are absent.
And the most influential screening evaluations \citep{oami2024screening,khraisha2024gpt4,matsui2024screening} report results from a single run, implicitly assuming that a repeat would yield the same result.

We address this gap with the following contributions:
\begin{enumerate}
  \item An open audit harness (\texttt{llm-repro-harness}) that runs a task $R$ times against each configured endpoint through one runner interface, emits a per-call record, and computes whole-output Exact Match Rate, pairwise disagreement, inter-run $\kappa$ and schema conformance;
  \item A measurement of run-to-run reproducibility for six deployment stacks over a two-stage environmental evidence pipeline (500 abstracts, 10 runs, 35{,}636 calls): exact reproduction on the local stacks, extraction EMR of 0.150--0.470 on the API-served stacks at temperature zero;
  \item A same-checkpoint comparison (Llama~3 8B Instruct local vs.\ cloud) showing that a model deterministic on one serving stack varied across runs on another, scoped to the differences in weight precision and request construction between the two arms;
  \item Tests of three settings practitioners rely on---a transmitted seed, a fixed-slot output shape, and a decision model that returns probabilities---none of which removed the variation;
  \item Evidence that schema conformance and accuracy are separate from reproducibility, and a documented provenance failure in which run cards recorded a temperature the client did not transmit, from which we derive reporting requirements for LLM steps in environmental workflows.
\end{enumerate}

\section{Related Work}

\subsection{LLMs in Systematic Reviews}

\citet{oami2024screening} evaluated GPT-4~Turbo for citation screening, reporting sensitivity of 0.75 and specificity of 0.99, with prompt tuning improving sensitivity to 0.91.
\citet{khraisha2024gpt4} extended this to multilingual screening and extraction with GPT-4 and found that, once chance agreement and dataset imbalance were adjusted for, performance was moderate for extraction and ranged from none to moderate for title/abstract screening.

For data extraction, \citet{gartlehner2024extraction} showed that Claude~2 achieved 96.3\% accuracy compared to human reviewers, with replication accuracies of 96.9\% and 95.0\%.
\citet{jensen2025chatgpt} found that ChatGPT-4o achieves 92.4\% extraction accuracy and 94.1\% inter-session reproducibility, explicitly noting residual stochasticity across sessions.

More comprehensive pipelines have also been proposed.
The TrialMind system \citep{wang2025trialmind} demonstrated that human-AI collaboration improved recall by 71.4\% and reduced screening time by 44.2\% across 100~systematic reviews.
\citet{li2025jamia} described an LLM pipeline for health technology assessment, while \citet{matsui2024screening} showed that a three-layer GPT-3.5/GPT-4 strategy achieved human-comparable sensitivity.
\citet{cao2025ottosr} presented otto-SR, a system that automates the entire systematic review lifecycle with LLMs, demonstrating near-human performance across screening, extraction, and synthesis---yet without examining run-to-run reproducibility.
\citet{khan2025collaborative} proposed a collaborative multi-LLM approach for automated data extraction in living systematic reviews, achieving high accuracy but reporting results from single executions.
A recent systematic review of automated meta-analysis \citep{li2025transforming} found that 52.5\% of 61 studies automate data processing and only one (about 2\%) attempts full-process automation---underscoring that evidence synthesis remains a multi-stage pipeline where each step introduces potential variation.

A common thread across these studies is that \textbf{reproducibility is either assumed or measured only superficially}.
Test-retest reliability, when reported, is based on 2--3~repetitions and does not examine how variation propagates through multi-stage pipelines.

\subsection{The Non-Determinism Problem}

\citet{atil2024nondeterminism} provided the most comprehensive analysis to date, documenting accuracy swings of up to 15\% across repeated runs and introducing the TARr@N metric to quantify run-to-run stability.
\citet{klishevich2025codereview} confirmed that temperature${=}$0 fails to ensure determinism across GPT-4o, Claude~3.5, and LLaMA~3.2 on code review tasks.

At the token level, \citet{fu2026beyond} showed that apparent text-level agreement masks substantial distributional instability in token probabilities---a finding that suggests surface-level reproducibility metrics may underestimate true variation.
\citet{angermeir2025icse} examined how non-determinism undermines reproducibility in software engineering research, proposing documentation standards to mitigate this.

These studies measure non-determinism on general-purpose tasks (benchmarks, code review, classification); none uses the structured, multi-field outputs of evidence extraction.

\subsection{Reproducibility in AI Research}

The broader AI reproducibility crisis has been documented extensively.
\citet{hutson2018science} identified unpublished code and sensitivity to training conditions as primary barriers.
\citet{haibe2020nature} called for structural reform, advocating for mandatory code and model sharing.
\citet{kapoor2023leakage} documented data leakage affecting 294~studies across 17~fields, while \citet{han2025biomedical} analyzed reproducibility failures in biomedical AI through the lens of model non-determinism.

Recent frameworks have attempted to systematize reproducibility requirements.
\citet{desai2025reproducibility} proposed a taxonomy of reproducibility types, arguing that LLMs require ``conceptual replicability'' given their proprietary training data.
\citet{semmelrock2025barriers} provided a systematic overview of barriers, and \citet{yu2024hdsr} argued that computational reproducibility alone is insufficient for trustworthy AI.

\subsection{Provenance and Transparency}

Provenance tracking---recording the lineage of data, computations, and decisions---has been identified as a key enabler of AI reproducibility.
\citet{longpre2024audit} audited 1,800+ datasets, finding license omission rates above 70\%.
\citet{liang2024modelcards} analyzed 32,111~model cards on Hugging Face, finding that documentation of limitations and environmental impact remains sparse.
The Foundation Model Transparency Index \citep{bommasani2024fmti} scored 14~major developers across 100~indicators, finding average transparency of only 58/100.

Technical solutions for provenance include the Workflow Run RO-Crate \citep{leo2024rocrate} and the W3C Provenance (PROV) Data Model---a W3C Recommendation defining an interoperable standard for representing the entities, activities, and agents involved in producing a piece of data \citep{kale2023provenance}.
\citet{longpre2024broken} argued at ICML~2024 that current practices for data authenticity, consent and provenance are broken, and called for provenance standards.

Our provenance approach builds on the lightweight protocol proposed by \citet{rover2026jair}, using SHA-256 hashing of inputs, outputs, and configurations to create an auditable trail without requiring infrastructure beyond standard file storage.

\subsection{Reproducibility of Environmental Modelling Workflows}

Work in this journal has approached the same problem from the modelling side. \citet{schlogl2026reproducibility} distinguish methodological, results and inferential reproducibility in geoscientific analysis and list ``non-deterministic model outputs from generative AI'' among the barriers, without measuring it. \citet{zhu2025geosimulation} assess the computational reproducibility of geo-simulation experiments workflow-wide and then process by process, a diagnosis that presumes a process behaves the same way when re-executed. On the LLM side, \citet{yoon2026hydropower} scale open-weight models for regulatory information extraction and fix temperature at zero to obtain consistent outputs from a single run, and \citet{park2026toolinterfaces} show that a typed, range-validated tool interface gives an LLM agent control and reviewable provenance in SWAT+ calibration without guaranteeing a valid model state. None of these measures whether an LLM-mediated step returns the same output when it is run again, which is the per-process property the present harness measures.

\subsection{Positioning: What Existing Studies Do Not Address}

Table~\ref{tab:comparison} synthesizes the landscape of prior work and highlights the methodological gaps that motivate our study.
Three critical gaps emerge.
\textbf{First}, studies that evaluate LLMs for evidence synthesis \citep{oami2024screening,gartlehner2024extraction,jensen2025chatgpt,matsui2024screening} measure accuracy against human judgments and either do not measure self-consistency across repeated runs or do so with 2--3~repetitions and per-field metrics that can mask whole-output variation (three-run screening consistency of 95.9--98.9\% ; \citealp{oami2025optimal}).
\textbf{Second}, studies that measure LLM non-determinism \citep{atil2024nondeterminism,klishevich2025codereview,fu2026beyond} do so on general-purpose benchmarks (classification, code review), not on the structured, domain-specific tasks characteristic of evidence synthesis.
\textbf{Third}, no study in Table~\ref{tab:comparison} measures whether extraction variation survives meta-analytic pooling, or holds the model checkpoint fixed while changing the serving stack inside an evidence-synthesis pipeline.
Our study addresses these gaps for one environmental evidence task.

\section{Methods}

\subsection{Study Design}

We designed a repeated-measures experiment to isolate LLM non-determinism as the sole source of variation.
We held the corpus, prompts, model configurations, and random seeds constant across all runs.
Differences between runs therefore arise from the model or its serving infrastructure, or from calls that failed, which EMR counts as non-matches (Section~\ref{sec:metrics_emr}).

Figure~\ref{fig:pipeline} provides an overview of the experimental pipeline.

\subsection{Unit of Analysis: Deployment Stacks}
\label{sec:unit_of_analysis}

We treat the unit of analysis as the \emph{deployment stack}---the tuple $(\textit{model\_weights},\,\textit{provider},\,\textit{infrastructure},\,\textit{API\_layer})$---rather than the model weights alone.
For the three local stacks, every component of the tuple is transparent and pinned: open-weight checkpoints with verifiable hashes (LLaMA~3 8B, Mistral~7B, Gemma~2 9B), served by Ollama~v0.15.5 on a single Apple~M4 chip (24~GB RAM, single replica, all layers on the on-chip GPU, one request at a time), through Ollama's local HTTP endpoint.
For the three API-served stacks, only the provider and the client-visible API surface are observable; the underlying weight checkpoint version, GPU topology, batching policy, and intermediate-precision routines are opaque and may change without notice.
This framing matters because the local-vs-cloud comparison constitutes a \emph{partial quasi-isolation probe}: when two stacks serve the same checkpoint (Llama~3 8B Instruct, a 4-bit quantization served locally via Ollama and the provider's version via DeepInfra) but differ in infrastructure and serving layer, divergence within each arm is attributable to the non-weight components of the tuple, while divergence between arms also reflects how each request was built and the weight precision each stack serves (Section~\ref{sec:desconfound}).
Throughout this paper we use ``deployment stack'' for the experimental unit and reserve ``model'' for the weights alone.

\subsection{Corpus Construction}
\label{sec:corpus}

We constructed a 500-abstract corpus from PubMed covering the association between PM$_{2.5}$ and respiratory health outcomes (Supplementary Table~S26).
We chose this domain because it is one of the most extensively studied areas in environmental epidemiology, with \citet{yu2024lancet} estimating approximately 1~million premature deaths annually from short-term PM$_{2.5}$ exposure.
Its time-series and case-crossover studies report relative risks or odds ratios with confidence intervals in a small set of formats, which gives the extraction step a defined numeric target.
Prior work on particulate matter and respiratory morbidity has shown that machine learning models can capture the complex, lagged relationships between PM$_{10}$ concentration and hospital admissions \citep{tadano2021unorganized}, further motivating a domain where both the epidemiological patterns and the computational methods are well established.


\noindent Inclusion criteria required: (1)~original epidemiological study, (2)~PM$_{2.5}$ as exposure, (3)~respiratory hospitalization or emergency-department visit as the outcome---mortality-only studies are \emph{excluded}, (4)~time-series or case-crossover design, (5)~a relative risk, odds ratio or equivalent effect measure reported with its confidence interval, and (6)~publication in English.
The screening prompt (\texttt{configs/prompts/screening.txt}) and the human labeling protocol state these six criteria; their exact wordings are reproduced in the Supplement.
Articles were sourced from PubMed using the E-utilities API with a broad query yielding 573~candidate records, supplemented by 475~exclusion candidates and a design-filtered subset of 222~records.
The final corpus spans 148~journals and publication years 1994--2026, with a mean abstract length of 1,873~characters.

\textbf{Reference labels.}
The 200~clear-category abstracts (100~include + 100~exclude) were labeled by an automated classification rule based on inclusion-criteria keyword matching; its agreement with human judgement is measured by the dual-human validation below, which contests the rule on its include side.
The 300~remaining abstracts received heuristic labels from the same rule operating in low-confidence regions and are explicitly flagged as not human-validated.
We do not present these heuristic labels as human labels, and we therefore \emph{exclude} them from the accuracy, sensitivity and specificity computations rather than reporting them separately: those metrics are computed against the 200 clear-category abstracts only, giving per-stack denominators of 192--200 rather than 500 (Table~\ref{tab:screening}).
We also record what this stratum is and is not. Of its 300 abstracts, 260 carry the maximum inclusion score of~5---the same score borne by all 100 clear-includes---and all 300 carry zero exclusion reasons. The label ``ambiguous'' therefore denotes low rule confidence, not measured human disagreement, and the stratum is closer in composition to the include side than the name suggests.

We additionally conducted a \textbf{dual-independent human-labeling validation} on a stratified subset of 100~abstracts (25~clear-include + 25~clear-exclude + 50~ambiguous, stratified by heuristic category $\times$ year-tertile, seed${=}$42).
The labeling protocol, screening templates, and agreement script were pre-registered on the Open Science Framework \emph{before} any label was collected (\url{https://doi.org/10.17605/OSF.IO/FGN3E}, frozen 2026-05-12; the two label sets were returned on 2026-07-15 and 2026-07-29).
Two reviewers, each blinded to the other's decisions and to every LLM output (the files they labeled carry only the bibliographic record and the abstract), independently classified every abstract via the protocol in Supplementary Section~S4; we computed Cohen's $\kappa$ on the 3-class outcome (include/exclude/uncertain) and on the binary include-vs.-exclude collapse.
Agreement fell \textbf{below the pre-specified target} of $\kappa{\geq}0.80$: $\kappa{=}0.529$ (SE${=}0.074$, 95\%~CI \ci{0.383}{0.674}) on the 3-class outcome and $\kappa{=}0.556$ (95\%~CI \ci{0.400}{0.712}) on the binary collapse, with 75\% raw agreement and 25~discordant abstracts (confusion matrix and full agreement statistics in Supplementary Section~S4).
The shortfall against the target is itself statistically decisive ($z{=}-3.65$, $p{=}1.3{\times}10^{-4}$), whereas $n{=}100$ is not sufficient to place $\kappa$ within a single descriptive band---the interval spans ``fair'' through ``substantial''---so we report the value against the threshold rather than assigning it a label.
Two objections can be foreclosed immediately. The low coefficient is not an artefact of skewed marginals: the prevalence index is 0.189 and PABAK (0.558 on the binary collapse) is nearly identical to $\kappa$, so the ``kappa paradox'' is not operating here. Nor is it an artefact of the three-class scale: linearly and quadratically weighted $\kappa$ (0.541 and 0.548, computed on the ordinal ordering include--uncertain--exclude) move the estimate by less than 0.02.
The pre-registration specified in advance what to do in this event---report the value transparently, examine the disagreement pattern qualitatively, amend the protocol to address the ambiguity, and file a sub-registration update---and that sequence was followed.
The disagreement is not diffuse but directional, and this is testable: the discordant cells of the binary table are 2~versus~19 (exact McNemar $p{=}2.2{\times}10^{-4}$), and marginal homogeneity is rejected on the full 3-class table (Stuart--Maxwell $\chi^2(2){=}16.4$, $p{=}2.7{\times}10^{-4}$), with a bias index of 0.179.
One rater is systematically more inclusive than the other, which is the signature of divergent protocol reading rather than of random rater noise.
The source is specific: 17~of those 19 asymmetric discordances turn on inclusion criterion~5 (a quantitative effect estimate), whose v1.1 wording supported two defensible readings---requiring the numeric estimate and interval to be present, or accepting an explicit statement that the study reported them.
The v1.1 decision table compounded this by specifying outcomes for failure in two or more criteria and for a borderline single criterion, but not for clear failure in exactly one, which is precisely the configuration of those 17~abstracts.
Neither rater departed from the protocol; the protocol was underspecified.
Protocol v1.2 therefore splits criterion~5 into three levels: values present (criterion satisfied), the effect stated but its values absent (\emph{uncertain}, since abstract-only screening cannot verify what the abstract omits), and no estimate or mention at all (\emph{exclude}, since total absence is reasonable evidence that no extractable estimate exists).
The amendment also separates structural criteria (original study, PM\textsubscript{2.5} exposure, respiratory hospitalization, English), where a single clear failure excludes, from conditional ones (design, effect reporting), where a single failure yields \emph{uncertain} unless the information is absent rather than merely unreported.
The pre-registered protocol routes the 25~discordant items to a blinded recalibration, a consensus meeting, with the senior author (Y.d.S.T.) as tie-breaker; no label from that sequence enters any number reported here, and $\kappa{=}0.529$ is the study's agreement estimate. Showing that the amended criterion repairs the ambiguity requires a fresh independent sample, not a re-rating of the same items; these data do not show it.

Stratifying agreement exposes something the pooled coefficient hides, and it bears directly on how our accuracy numbers should be read.
On the 25~clear-\emph{exclude} abstracts the two raters agreed unanimously (25/25, PABAK${=}1.00$; $\kappa$ is undefined there because expected agreement equals one---a degenerate-marginals case that is precisely why we report PABAK alongside).
On the 25~clear-\emph{include} abstracts agreement was 68\% ($\kappa{=}0.359$), and on the 50~ambiguous abstracts 66\% ($\kappa{=}0.398$).
The automated rule's include side fares worst under human scrutiny: of the 25~abstracts it called clearly includable, one rater endorsed inclusion for 13 and the other for 21, and 8~of the 25~discordances fall inside that stratum.
The reference is therefore \textbf{asymmetrically valid}. Specificity rests on the unanimous exclude side, whose labels are firm but which was drawn by a query for animal, in-vitro and occupational studies, so it measures rejection of clearly off-topic records, not of near-miss studies. Sensitivity rests on include-side labels that the human raters substantially contest, so its error has no known direction: a stack loses credit for correctly rejecting a mislabelled include and gains it for accepting one, and a stack that responds to the same surface features as the rule is favoured. We therefore do not interpret sensitivity differences between stacks.

For extraction, we constructed two independent reference standards: (a) a \emph{silver-internal} consensus from majority vote across all 6~stacks $\times$ 10~runs (60~votes per item), and (b) a \emph{silver-external} consensus from DeepSeek-R1 (5~runs $\times$ 100~items, majority vote per field).
DeepSeek-R1 was selected for the silver-external role because it is served by a provider outside those evaluated here; independence of its errors from those of the evaluated stacks is not established, so the silver-external standard serves as a comparative anchor, not as a reference of truth.
Cross-validation between these two silvers yields Spearman $\rho{=}0.845$ on \texttt{effect\_estimate} and 80\% agreement across numeric fields (consensus subset, see Supplementary Section~S14), supporting their use as comparative anchors.
The extraction set is the 100 abstracts the automated rule labels as includes; of the 25 of them in the human-labelled subset, only 13 are included by first-round human agreement, and 15~abstracts the raters agree to include are outside it. No dual-human extraction reference was built for this study, so extraction accuracy is reported against the two silver standards only.

Because our primary metric (EMR) measures self-consistency rather than accuracy, gold-standard quality affects only the secondary accuracy analysis; we report secondary accuracy against the automated rule's labels (screening) and against the silver-internal and silver-external standards (extraction; the latter on its consensus subset only, see Supplementary Section~S14).
Given the asymmetric validity documented above, we treat the exclude side of every accuracy comparison as firm and the include side as uninterpretable.

\subsection{Sources of Non-Determinism in Distributed Inference}
\label{sec:mechanisms}

It is useful to distinguish two classes of factors that can plausibly contribute to LLM non-determinism across deployment stacks.
\emph{Cloud-deployment factors} are those intrinsic to running a model on hardware accessed over a network: end-to-end network latency, request routing across geographically distributed endpoints, shared physical hardware, and multi-tenancy isolation policies.
\emph{Production serving-infrastructure factors} are specific design choices in the LLM inference stack: tensor parallelism with non-deterministic all-reduce, FlashAttention kernel non-determinism, dynamic continuous batching that varies request composition between calls, speculative decoding fast-paths, mixed-precision (BF16/FP16) accumulation, and prefix-caching state shared across requests.
These two classes are conceptually distinct: a request that traverses the network can still be served on a deterministic infrastructure, and vice versa, an infrastructure with the non-deterministic features above can be exercised under local-network conditions.
Our same-checkpoint comparison (Section~\ref{sec:desconfound}) holds the checkpoint constant while varying the rest of the stack tuple, including weight precision and the request payload, so it does not separate the two classes.

\noindent Supplementary Table~S27 maps six of these mechanisms onto each of the six deployment stacks studied here, classifying each cell as documented (\checkmark), \emph{likely} (consistent with public information from the provider's serving infrastructure), \emph{possible} (compatible with public information but not directly confirmed), or precluded by stack design (---).
Attribution is necessarily \emph{inferential} for the API-served stacks because the production serving stacks of OpenAI, Anthropic, and Google are closed-source; the table reflects what is publicly documented or strongly implied by published architecture descriptions, not what we directly measured per request.


\noindent The mapping is used in two ways in our discussion.
First, the residual disagreement observed in the same-checkpoint cloud experiment (Section~\ref{sec:desconfound}) is compatible with mechanisms 1--4 and with the precision and request differences described there; the design does not discriminate among them.
Second, the larger gap observed for the three API-served stacks of much-larger proprietary weights is consistent with all six mechanisms being active simultaneously; we therefore do not attribute it to any single mechanism.

\subsection{Prompt Development}
\label{sec:prompts}

Both prompt templates (Supplementary Listings~S3 and~S4) were developed over two pilot rounds before the main experiment.

\textbf{Round~1.}
An initial draft was tested on 10~randomly drawn abstracts from the corpus (5~include + 5~exclude) using LLaMA~3 8B locally.
Output JSON validated against the schema for 9 of 10~calls; one failure was due to embedded Markdown code-fences.
The failure case motivated the explicit instruction ``Respond with a JSON object only. Do not include any text outside the JSON.''~in both prompts.

\textbf{Round~2.}
The revised prompt was tested on the same 10~abstracts plus 10~additional abstracts drawn from the ambiguous stratum.
Output validated for 20/20 calls.
We additionally manually inspected the rationale text for coherence (no contradictions between rationale and decision); none were identified.

The final prompts (repository commit \texttt{75292f2}) were held constant across all 6~stacks and all 120~experimental runs.
We did not adapt prompts to individual model capabilities beyond the generic JSON-only constraint, as such adaptation would confound model-level effects with prompt-level optimization.
A formal \emph{prompt sensitivity analysis}---varying the structured-output shape (variable-length estimates array vs.\ fixed-slot single primary estimate)---is reported in Section~\ref{sec:fixedslot}.

\subsection{Pipeline Stages}

Each deployment stack was run 10~times through two stages. Every request carried the title and abstract twice, once inside the filled template and once appended after it; this construction is identical for every stack in Table~\ref{tab:models} and in both stages.

\textbf{Stage A: Abstract Screening.}
Each of the 500~abstracts was presented with a structured prompt requesting a JSON response containing: a binary decision (\texttt{include}/\texttt{exclude}), a confidence score (0--1), and a brief rationale.
Note that LLaMA consistently processed 480 of 500~abstracts per run (the same 20~abstracts returned output that was not valid JSON in every run); the remaining models processed all 500.
Total: $6 \text{ stacks} \times 10 \text{ runs} \times 500 \text{ abstracts} = 30{,}000$ screening calls.

\textbf{Stage B: Data Extraction.}
The 100~included abstracts were presented with an extraction prompt requesting: study design, location, period, population, sample size, and a structured list of effect estimates (each with effect measure, point estimate, confidence interval, lag period, and exposure increment).
LLaMA consistently processed 96 of 100~articles per run (the same 4~articles returned output that could not be parsed as JSON); the remaining models processed all 100.
Total: $6 \text{ stacks} \times 10 \text{ runs} \times 100 \text{ articles} = 6{,}000$ extraction calls.

In total, the experiment issued \textbf{36{,}000~LLM calls}, of which 35{,}636 returned an output, across \textbf{120~experiment runs}. Stage~B receives the same 100 rule-labelled INCLUDE abstracts regardless of any stack's Stage~A decisions, so screening variation does not propagate into extraction in this design.

\subsection{Reproducibility Metrics}

\subsubsection{Exact Match Rate (EMR)}
\label{sec:metrics_emr}

Our primary metric is the \emph{Exact Match Rate}, defined as the proportion of items (abstracts or articles) that received identical outputs across all 10~runs:

\begin{equation}
  \emr = \frac{1}{N} \sum_{i=1}^{N} \mathbb{1}\!\left[\,\left|\{o_{i,1}, o_{i,2}, \ldots, o_{i,R}\}\right| = 1\,\right]
\end{equation}

\noindent where $N$ is the number of items submitted (500 for screening, 100 for extraction), a failed call entering as its error output, $R{=}10$ is the number of runs, $o_{i,r}$ is the output for item~$i$ in run~$r$, and $|\cdot|$ denotes the number of distinct values.
For screening, $o_{i,r}$ is the binary decision; for extraction, $o_{i,r}$ is the SHA-256 hash of the full JSON output (used as a compact identity check: any character-level difference produces a different hash).

An $\emr$ of 1.0 indicates perfect reproducibility; an $\emr$ of 0.0 indicates that every item received at least one different output across runs.
We note that extraction EMR is a strict metric---any variation in any field (including formatting differences such as ``Beijing, China'' vs.\ ``Beijing'') produces a non-match.
The field-level analysis in Section~\ref{sec:fieldlevel} complements this by isolating which fields drive the variation.

\subsubsection{Bootstrap Confidence Intervals}

We computed 95\% confidence intervals for EMR using the percentile bootstrap method with 10,000~resamples.
For each bootstrap sample, we drew $N$ items with replacement and computed the EMR, then reported the 2.5th and 97.5th percentiles of the bootstrap distribution.
We note that when $\emr{=}1.000$ (as for all local stacks), the percentile bootstrap trivially returns $\ci{1.000}{1.000}$.
By the rule of three \citep{hanley1983ruleofthree}, observing zero non-matches in $N{=}500$ items yields a 95\% one-sided upper bound on the true non-match rate of $3/500{=}0.006$; thus, we can rule out population-level non-determinism rates above 0.6\% for local models, but not lower rates.

\subsubsection{Secondary Metrics}

\begin{itemize}
  \item \textbf{Flip rate}: $1 - \emr$ (proportion of items with any variation across runs)
  \item \textbf{Mean agreement}: Average proportion of runs agreeing with the majority decision per item
  \item \textbf{Accuracy vs.\ reference labels}: Per-run sensitivity, specificity, and accuracy against the automated rule's labels on the 200 clear-category abstracts
  \item \textbf{Field-level EMR}: For extraction, the proportion of articles with identical values for each individual field across all runs
  \item \textbf{Estimate count stability}: The proportion of articles for which all 10~runs extracted the same number of effect estimates---a measure of structural consistency independent of the specific values extracted
\end{itemize}

\subsection{Provenance Protocol}
\label{sec:provenance_protocol}

\textbf{Scope: client-side observability.}
The provenance protocol described below records only what is observable from the client.
It documents what is observable from the client side---the request payload, the resolved model identifier and version returned by the API (when available), response headers, the client-recorded API response identifier, end-to-end latency, and the input/output text together with their cryptographic hashes.
It does not require provider-side weight hashes, GPU-topology fingerprints, or batching-policy attestation, none of which are returned by any production LLM API at the time of writing.
The protocol is therefore not restricted to open-source local stacks: for proprietary API-served stacks, it records the client side of each call, the only side a proprietary API exposes.
Its operational value is twofold: (i)~\emph{differential diagnosis}---when the same prompt produces different outputs at the same client-pinned snapshot, identical call hashes rule out drift in the declared prompt, input and configuration, but not a difference between the declared and the transmitted request (Finding~9); and (ii)~\emph{provider-agnostic minimum standard}---adopting the protocol creates a verifiable audit trail across any combination of local and API-served stacks that authors may choose to use.
Weight-checkpoint hashes and deterministic-execution attestation would have to come from providers.

Following \citet{rover2026jair}, we implemented a lightweight provenance protocol that creates a cryptographic fingerprint of every input-output pair, enabling automated detection of any change across runs:
\begin{itemize}
  \item \textbf{Call-level hashing}: SHA-256 hash of a canonicalized JSON object of the prompt template, input text, model ID, temperature and seed, serialized with sorted keys and ASCII encoding to ensure deterministic hashing across platforms; absent parameters (e.g., Claude's seed) are encoded as \texttt{null}. The Claude stack's records add a sixth field naming the hash basis, the same-checkpoint cloud arm was hashed by its own script over a differently formatted input, and the decision-model records carry no call hash
  \item \textbf{Output hashing}: SHA-256 hash of the raw response text
  \item \textbf{Run cards}: Structured JSON metadata per run, including timestamps, token counts, success/failure rates, and aggregate output hashes
\end{itemize}

\noindent The call hash covers the declared configuration, not the transmitted request body. For the Claude stack, each call record additionally stores the temperature read back from the request body as sent (\texttt{request\_temperature}); the runners of the other stacks place the declared temperature in the request body unconditionally.
The protocol is the one proposed in our companion paper \citep{rover2026jair}, which applies it to nine deployment stacks and six task families with five repetitions per item; the present study applies it to a two-stage pipeline over 500 abstracts at 10~repetitions.

\noindent This protocol enables post-hoc verification: if two runs produce different aggregate hashes, the per-call hashes pinpoint exactly which items changed.

\section{Results}

\subsection{Overview}

Local stacks reproduced every output, in both stages, across ten runs; API-served stacks did not, and the gap widened from screening (EMR 0.936--0.990) to extraction (0.150--0.470).
All 120~experiment runs were executed: 60~screening runs (10~per stack $\times$ 500~abstracts) and 60~extraction runs (10~per stack $\times$ 100~articles), 36{,}000~calls in all, 35{,}636 of which returned an output.
LLaMA consistently processed 480/500 screening abstracts and 96/100 extraction articles across all 10~runs---the same 20 screening and 4 extraction items failed every time, producing identical error outputs.
In screening these failures are not truncation: every such generation ended normally, and inspection shows text that JSON does not admit, such as a comment written after a value; in extraction, one of the four items reached the 2{,}048-token ceiling in every run. Parsed outputs that violate the schema (for example \texttt{case-crossover} where the schema fixes \texttt{case\_crossover}) are not failures; they are counted as non-conforming in Section~\ref{sec:conformance}.
Because these failures were deterministic (the same items failed identically in every run), they contribute to perfect agreement; EMR was computed over all 500 (screening) and 100 (extraction) items.\footnote{Computing EMR over only the 480 successfully parsed items yields the same result ($\emr{=}1.000$), since the 20 consistently-errored items also agree across runs.}
GPT-4.1 achieved 500/500 screening and 100/100 extraction in all runs, and Claude did the same except for two screening calls in one run that failed on the network and returned no decision; those two abstracts count as non-matches in its EMR.
Mistral processed 497/500 screening abstracts and Gemma 493/500, in both cases failing the same items identically in every run, so the footnote above applies to them as well.
Gemini achieved 483--500/500 screening and 98--100/100 extraction.

Among the cloud APIs, Claude showed a 1.0\% flip rate (5~abstracts, two of them the network failures noted above; as for every stack, a failed call counts as a non-match, and without those two the rate is 0.6\%), GPT-4.1 3.0\% (15~abstracts), and Gemini 6.4\% (32~abstracts, 17 of them involving a failed call; 15 in which every run returned a decision).

Notably, accuracy and reproducibility behaved as independent properties: Gemini achieved the highest accuracy (0.964) and a reproducibility ($\emr{=}0.936$) below Claude's (paired McNemar, Holm-adjusted $p{<}0.001$; Supplementary Table~S18) and not distinguishable from GPT-4.1's, while Mistral had perfect reproducibility but the lowest accuracy (0.628) due to an include-biased strategy (sensitivity${=}$1.000, specificity${=}$0.240).
This illustrates that a stack can be accurate on average yet inconsistent across individual runs, and conversely, that perfect reproducibility does not imply high accuracy.

\medskip
\noindent\textbf{Inter-run agreement (Fleiss' $\kappa$).}
As a chance-corrected complement to EMR, we computed Fleiss' $\kappa$ across the 10 runs on the 3-class screening decision (include/exclude/uncertain) for each deployment stack.
Inter-run Fleiss' $\kappa$ for screening ranged from $0.974$ (GPT-4.1) to $1.000$ (all three local stacks); the cloud APIs were $\kappa{=}0.995$ (Claude), $0.975$ (Gemini), and $0.974$ (GPT-4.1).
These values quantify self-consistency across repetitions of the same stack and are not directly comparable to the $\kappa{\geq}0.80$ target we pre-specified for agreement between two human reviewers, which concerns a different construct (see Section~\ref{sec:metric_pairing}).
For whole-output extraction (each unique output hash as a distinct rating category), the picture is dramatically different: Claude's inter-run $\kappa{=}0.757$, Gemini's $\kappa{=}0.505$ and GPT-4.1's $\kappa{=}0.512$; local stacks retain $\kappa{=}1.000$. Because each output hash is its own category, chance agreement is near zero and these values approximate one minus the pairwise disagreement of Table~\ref{tab:extraction}; we attach no descriptive band to them.
Full Fleiss' $\kappa$ values with 95\% CIs and per-categorical-field decompositions are reported in Supplementary Table~S19.

\subsection{Field-Level Analysis}
\label{sec:fieldlevel}

Not all extraction fields are equally affected (Supplementary Table~S29).


\noindent A clear pattern emerges: \textbf{categorical fields} (study design, study period) are highly reproducible even for API-served stacks ($\emr{\geq}0.990$), while \textbf{free-text fields} (study location) and \textbf{numerical extractions} (effect estimates) show the greatest variation.
GPT-4.1 is notable for achieving perfect location reproducibility (1.000) while showing variation in categorical fields like study design and period (0.990 each)---a different instability profile from Claude and Gemini, where location is the most variable field.

The estimate count stability metric reveals that 26.5\% of Gemini's articles with extractable estimates, 7.8\% of GPT-4.1's, and 2.2\% of Claude's received a different number of effect estimates across runs.\footnote{Estimate count stability is computed over articles that produced at least one estimate in all 10~runs, yielding denominators of 83 (Gemini), 90 (GPT-4.1), and 89 (Claude) rather than the full 100. The meta-analytic ``Varying'' column in Supplementary Table~S20 uses the full 100-article denominator, producing different percentages (20\%, 5\%, 1\%), since both the numerator and the denominator change.}
This structural variation directly affects any downstream meta-analysis.

\subsection{Semantic Equivalence Analysis}
\label{sec:semantic}

The hash-based EMR reported in Table~\ref{tab:extraction} (0.150 for GPT-4.1, 0.200 for Gemini, 0.470 for Claude) treats any character-level difference in the \emph{full JSON output}---including all numeric effect estimates, confidence intervals, and variable-length estimate arrays---as a mismatch.
To disentangle variation in the five metadata fields from variation in numeric estimates, and to assess whether metadata variation is merely cosmetic (formatting, abbreviation) or genuinely semantic, we applied three progressively relaxed string criteria and one embedding-based criterion to the metadata fields only (Supplementary Table~S30).

\begin{enumerate}
  \item \textbf{Exact match}: character-identical outputs (equivalent to SHA-256 hash comparison).
  \item \textbf{Normalized match}: after lowercasing, whitespace normalization, punctuation stripping, and abbreviation expansion (e.g., ``U.S.'' $\to$ ``United States'').
  \item \textbf{Fuzzy match}: Levenshtein similarity ratio $\geq\!0.90$ between all normalized pairwise comparisons across runs.
  \item \textbf{BERTScore}: Embedding-based semantic similarity using \texttt{roberta-large}, computing the F1 score across all $\binom{10}{2}{=}45$ unique run pairs per article (4,500~pairs per stack).
\end{enumerate}


\noindent Four findings emerge from this multi-level analysis.

\textbf{First}, the gap between metadata-field EMR and hash-based EMR quantifies how much variation resides in the numeric estimate arrays versus the text metadata.
For Claude, 93\% of articles had identical metadata across all runs, but only 47\% had identical \emph{complete} outputs; for GPT-4.1, 88\% had identical metadata but only 15\% had identical complete outputs; for Gemini, 62\% and 20\% respectively.
In all three cases, the variable-length estimate arrays (effect sizes, confidence intervals) are the primary source of non-reproducibility.

\textbf{Second}, within the metadata fields, normalization and fuzzy matching improved EMR by at most 1~percentage point (Gemini: 0.620~$\to$~0.630; Claude: 0.930 and GPT-4.1: 0.880 unchanged), showing that the variation is not a formatting artefact: the values themselves differ.

\textbf{Third}, BERTScore embedding similarity computed across all $\binom{10}{2}{=}45$ unique run pairs per article (4,500~pairs per stack) was near-perfect for all API-served stacks: GPT-4.1 averaged $F_1{=}1.000 \pm 0.004$, Claude $F_1{=}0.999 \pm 0.004$, and Gemini $F_1{=}0.997 \pm 0.022$, with 100\%, 100\%, and 98.5\% of pairs exceeding $F_1{\geq}0.95$, respectively. These means include the identical pairs, which dominate, so they say little about the pairs that differ.
This creates an apparent paradox: the models produce \emph{semantically near-identical} metadata text, yet 53--85\% of their complete extraction outputs are non-identical.
The resolution lies in the numeric estimates---the effect sizes, confidence intervals, and variable-length estimate arrays that hold hash-based EMR at 0.150--0.470.
Even when a model describes a study in nearly the same words, it may extract a different number of effect estimates or parse ``RR${=}$1.05 (95\% CI: 1.01--1.09)'' with subtly different numeric precision.
Concrete, verbatim side-by-side excerpts of an exact-match local-stack output and a near-miss API-stack output (with the divergence located in the variable-length \texttt{estimates} array rather than in the metadata fields) are reproduced as JSON listings in Supplementary Section~S5.

\textbf{Fourth}, the three API-served stacks exhibit distinct instability profiles.
Claude shows the highest metadata stability (exact EMR${=}$0.930) and the highest hash-based EMR (0.470), yet more than half of its complete outputs still differ across runs, which places its residual variation in the numeric layer.
GPT-4.1 shows high metadata stability (0.880) and the highest BERTScore ($F_1{=}1.000$), yet its hash-based EMR (0.150) is below Claude's and not distinguishable from Gemini's (Supplementary Table~S18), so numeric extraction drives its variation even more strongly.
Gemini shows the lowest minimum BERTScore ($F_1{=}0.754$) and highest standard deviation (0.022), indicating that some articles receive genuinely divergent interpretations across runs---not merely numeric rounding differences.

\subsection{Downstream Propagation}
\label{sec:metaprop}

An audit of an extraction step is only as interesting as what the step feeds. We therefore
propagated each run's extracted estimates into a pooled analysis, to ask whether run-to-run
variation survives aggregation or is averaged away.

The pooled quantity is a propagation instrument, not an estimate of the PM$_{2.5}$ effect: estimates
were pooled on the log scale as extracted, without harmonizing exposure increment, lag, outcome or effect
measure. Over the full corpus the run-to-run variation is largely averaged away: no run moves the pooled
95\% interval across RR${=}1$. The variation surfaces at small $k$. Resampling subsets of ten studies,
the share of subsets whose conclusion flips depending on which run supplied the inputs reaches
at most 2.0\% under DerSimonian--Laird and as much as 45.0\% under the Hartung--Knapp--Sidik--Jonkman
correction, both on the Gemini stack; for GPT-4.1 the HKSJ figure is 21.5\%, and for Claude and the
three local stacks no subset flips. A second, quieter effect is that $k$ itself moves with the
run---on the Gemini stack between 39 and 45 articles yield a usable estimate depending on the
execution---so non-determinism changes not only the numbers entering the pool but how many there are.

Because the pooling machinery is peripheral to the audit itself, the full analysis, the
per-run inputs and the heterogeneity statistics are reported in Supplementary Section~S19.

\subsection{Same-Checkpoint Comparison Across Serving Stacks}
\label{sec:desconfound}

Throughout the comparisons above, the local versus cloud difference is confounded with model size: our three local models are 7--9B-parameter open-weight models, while the three cloud APIs are estimated at $>$100B parameters and trained with proprietary procedures.
To probe the deployment effect, we ran an additional condition: the same Llama~3 8B Instruct checkpoint served via cloud (\texttt{meta-llama/llama-3-8b-instruct}, OpenRouter routing pinned to the DeepInfra provider) at temperature${=}$0 and seed${=}$42. The local stack serves Ollama's 4-bit (Q4\_0) quantization of that checkpoint; the provider does not disclose the precision it serves.
Ten cloud runs $\times$ 500~abstracts mirror the local experimental design.

The two arms hold constant the checkpoint, the prompt source file, the decoding temperature and the seed; they differ in weight precision and in the request payload. The harness client used for every main stack fills the template's title and abstract slots and then appends the title and abstract a second time; the cloud script sends a single user message containing the template with its \texttt{\{title\}} and \texttt{\{abstract\}} placeholders left unfilled, followed by the article once. The two were also configured with different output-token ceilings (2{,}048 local, 512 cloud). Measured over the deposited call records, the arms differ by 34.2\% in mean input tokens (1{,}279.3 local vs.\ 842.3 cloud). The comparison therefore shows how each arm behaves across its own repeated runs; it does not isolate the serving infrastructure from weight precision or from payload construction, and it covers screening only.
Output truncation is excluded as a contributor by direct measurement: all 4{,}266 completed cloud calls returned \texttt{finish\_reason}${=}$\texttt{stop}, none hitting the 512-token ceiling.

\noindent Three findings stand out.

\textbf{First, a small-parameter model became non-deterministic when served through a different stack.}
Local LLaMA~3 8B is bit-deterministic ($\emr{=}1.000$ over 10~runs and 500~abstracts).
The same model served via cloud is \emph{not}: 2.04\% of items receive different decisions in at least one run-pair (mean pairwise disagreement 0.79\%).
Small model size therefore does not by itself ensure determinism. Because the two stacks also differ in weight precision and request construction, the result does not separate serving infrastructure from either.

\textbf{Second, the two arms reach different decisions.}
Even within the runs where the cloud was internally consistent, mean pairwise agreement with the local deployment was 59.7\%.
Comparing the canonical run of each arm, of 430~items where both deployments produced a valid decision, 167 (38.8\%) showed a different decision under cloud than under local.

\textbf{Third, the discordance is asymmetric.}
Of those 167~discordant items, \textbf{all 167} were cases where the local model said \emph{include} but the cloud said \emph{exclude}; the reverse direction (local exclude / cloud include) occurred zero times.
The direction is systematic, and it cannot be assigned to the serving stack: the two arms rendered the request differently (the cloud prompt showed the template slots unfilled) and served different weight precisions, so serving-side numerics, quantization and payload construction are all candidates and this design does not discriminate among them. The within-arm result is unaffected, because each arm repeated its own payload unchanged.

We additionally observed an operational reliability finding: 2 of 10~cloud runs (\texttt{run\_005}, \texttt{run\_006}) experienced transient infrastructure failures that reduced their successful-call counts substantially (45/500 and 221/500 versus the ${\sim}$491/500 baseline of the other eight runs).
This pattern was absent from all 10 local Ollama runs, all of which had identical 480/500 success.
Cloud reliability is therefore a second property to report alongside reproducibility.

\subsection{A Decision Model on the Screening Stage}
\label{sec:jev}

The generative stacks sample one answer per call. A decision model returns the whole distribution, and a natural expectation is that a stack which never samples should never disagree with itself. The Jev arm tests that expectation on Stage~A.

It completed 4{,}998 of 5{,}000 calls; the two failures were a server error and a dropped connection. Screening EMR was 0.956 (95\% CI \ci{0.938}{0.972}): 20 abstracts received a different decision in at least one run and the two failed calls add two non-matches, within the range of the generative API stacks (0.936--0.990). Against the same reference labels as Table~\ref{tab:screening}, accuracy was 0.888, specificity 1.000 and sensitivity 0.776, the lowest sensitivity of any stack in Table~\ref{tab:screening}.

The probabilities show where the variation comes from. The probability of the chosen option varied across the ten runs by 0.039 on average, reached 0.20, and was zero for only 29.8\% of abstracts. Per option the picture is the same. For the same abstract and the same question, the probability Jev assigned to \emph{include} was identical across all ten runs for only 31.4\% of abstracts; its range across runs averaged 0.037 and reached 0.19, and over all three options the largest range was 0.20. Most of this movement does not change the decision, because the modal option carried a mean probability of 0.865 and fell below 0.5 for 4.4\% of abstracts. Returning the distribution therefore does not remove run-to-run variation. Abstracts whose probabilities move between runs can be identified from the output; whether routing them to a human reader improves screening was not tested. We make no calibration claim from these data: the human-labelled subset ($n{=}100$) is too small to estimate one. Call-level details are in Supplementary Section~S24.

\section{Discussion}

\subsection{Principal Findings}

Among the studies in Table~\ref{tab:comparison}, this is the only one combining whole-output metrics, ten repetitions and propagation of extraction variation into pooled estimates.

\textbf{Reframing: the object of reproducibility variation is the deployment stack, not the model.}
A first-principles consequence of our results is that ``which model'' is the wrong level of abstraction for talking about LLM reproducibility.
A deployment stack---the tuple of weights, provider, infrastructure, and API layer (Section~\ref{sec:unit_of_analysis})---is the unit through which an LLM actually generates an answer, and it is the unit at which reproducibility is preserved or destroyed.
Two stacks that share a checkpoint need not share determinism: the same 8B model reproduced exactly on the local stack and varied on the cloud stack (Table~\ref{tab:desconfound}); two stacks that differ in weights but share a deterministic local infrastructure can both achieve $\emr{=}1.000$ (Tables~\ref{tab:screening},~\ref{tab:extraction}).
Reporting only the model name in an LLM-assisted SR therefore underspecifies the experimental condition: the same checkpoint on a different stack did not reproduce the same outputs here.
This reframing motivates the recommendations in Section~\ref{sec:recommendations}.

\textbf{Finding 1: Determinism belonged to the local single-device stacks, and a small model lost it when served in the cloud.}
All three local stacks---LLaMA~3 8B, Mistral~7B, and Gemma~2 9B served via Ollama on a single device---produced identical outputs across all 10~runs in both screening and extraction.
All three cloud-based APIs (Claude, Gemini, GPT-4.1) exhibited measurable non-determinism despite transmitting temperature${=}$0 and, where the API accepts one, a fixed seed.
The same-checkpoint comparison (Section~\ref{sec:desconfound}) shows that small model size does not confer determinism: the 8B model that reproduced exactly on the local stack left 2.04\% of abstracts with a discordant run pair (mean pairwise disagreement 0.79\%) when served through DeepInfra. It covers screening only and differs between arms in weight precision and request construction, so it does not show that size plays no part in the extraction gap. The gap is consistent with floating-point non-associativity under multi-GPU serving \citep{karelin2024indeterminism}, where partial sums are reduced in an order that can change between calls, whereas a single device serving one request at a time can repeat the same order; the design does not isolate that mechanism. An INT4-quantized serving of the same model through a different cloud provider reproduced exactly on a 10-abstract extraction task in our companion study \citep{rover2026jair}, so the variation observed here belongs to this serving stack, not to cloud serving as such.

\textbf{Finding 2: The whole extraction output varies far more often than the screening decision, and the variation is in content, not formatting.}
Claude's EMR dropped from 0.990 (screening) to 0.470 (extraction); GPT-4.1's from 0.970 to 0.150; Gemini's from 0.936 to 0.200.
Screening requires a binary decision (a single token effectively determines the output), while extraction generates complex structured JSON with multiple fields.
The two EMRs are computed on different outputs---the decision alone versus the full JSON---so the drop does not measure how much the task itself amplifies non-determinism. The semantic analysis (Section~\ref{sec:semantic}) shows that the extraction gap is not an artifact of strict string matching: metadata text is near-identical across runs (BERTScore $F_1{\geq}0.997$, a mean dominated by identical pairs), yet hash-based EMR remained at 0.150--0.470.
This paradox reveals that the variation concentrates in the numeric extraction layer: the models describe studies in nearly the same words but extract different numbers of effect estimates and parse numeric values with different precision.
Even the residual metadata variation is in content (fuzzy matching recovers at most 1~percentage point), not formatting.
The practical implication depends on context: the high BERTScore ($F_1{\geq}0.997$) indicates that API-served stacks describe studies in near-identical terms, and for applications requiring only qualitative summaries, this level of consistency may be acceptable.
However, for quantitative evidence synthesis---where exact numeric values feed directly into meta-analytic pooling---the hash-based EMR of 0.15--0.47 represents a genuine threat to reproducibility.

\textbf{Finding 3: API-served stacks exhibit distinct instability profiles.}
Claude achieved the highest metadata stability among API-served stacks (exact EMR${=}$0.930), the smallest structural variation ($\Delta k{=}2$ estimates across runs) and the highest hash-based extraction EMR (0.470), yet more than half of its complete outputs still differed across runs.
GPT-4.1 paired high metadata stability (0.880, BERTScore $F_1{=}1.000$) and a small structural swing ($\Delta k{=}4$) with a hash-based EMR of 0.150, while Gemini showed the widest structural swing ($\Delta k{=}17$) and the most extreme semantic divergence (minimum BERTScore $F_1{=}0.754$).
These distinct profiles suggest that non-determinism manifests differently across API providers---some vary primarily in numeric precision, others in structural composition, and others in semantic interpretation.

\textbf{Finding 4: Accuracy and reproducibility are independent properties; report them as a paired tuple.}
\label{sec:metric_pairing}
Gemini achieved the highest screening accuracy (0.964) and a screening reproducibility (0.936) below Claude's, while Mistral had perfect reproducibility (\emr{=}1.000) but a degenerate ``always-include'' strategy (specificity${=}$0.240, accuracy${=}$0.628).
This independence means that \textbf{accuracy evaluations from a single run cannot detect reproducibility problems}, and \textbf{reproducibility evaluations without accuracy cannot detect degenerate strategies}.
EMR and accuracy should be reported as a paired tuple, never EMR alone.

\textbf{Finding 5: Constraining the output shape did not remove the variation.}
In the fixed-slot test (Section~\ref{sec:fixedslot}), read against a run-count- and identity-matched baseline, fixed-slot EMR was lower on Gemini ($-55\%$, outside the fixed-slot interval) and not distinguishably different on GPT-4.1 ($+23\%$) and Claude ($-6\%$). The test is one three-run execution per stack, two months after the baseline for Gemini and GPT-4.1, so it shows only that the output shape did not account for the variation here.

\textbf{Finding 6: Neither a transmitted seed nor temperature zero delivers determinism.}
Recent reporting guidance for GenAI-assisted evidence syntheses asks authors to document random-seed values and, for commercial models, API versions and access dates \citep{farotimi2025rsm_genai_guidance}; it does not establish whether a documented seed delivers determinism.

The direct evidence needs no cross-provider comparison. Gemini and GPT-4.1 both expose a seed parameter, both received seed${=}$42 on every one of their 6{,}000 calls, and both clients place \texttt{temperature}${=}$0 in every request body (verified in the client code). Under those conditions---the exact configuration a practitioner would adopt believing it buys reproducibility---their extraction EMR was 0.200 and 0.150 respectively, against 1.000 for local stacks holding the same nominal settings. A documented, accepted, transmitted seed therefore does not make an API-served extraction pipeline reproducible.

The data also contain an observation that runs against the seed's reputation, and we state it with its limit. The most reproducible API-served stack on extraction was the one that accepts no seed at all: Claude, at temperature${=}$0 and without a seed, reached 0.470 against 0.200 and 0.150 for the two seeded stacks. That is a contrast between stacks that differ simultaneously in provider, infrastructure and API layer, so it is not an estimate of the seed's effect---our own unit-of-analysis argument in Section~\ref{sec:unit_of_analysis} forbids that reading---but it is incompatible with the seed being what separates reproducible from non-reproducible API stacks.
What our design does \emph{not} support is an estimate of how much the seed contributes on its own. Such an estimate requires a within-stack ablation---the same stack, same provider, same infrastructure, run with and without the seed---and we did not execute one.

Temperature behaves the same way. The Claude execution in which the client omitted the temperature field, so that calls ran at the API default of~1.0 (Finding~9; Supplementary Section~S23), gives a contrast: its extraction EMR was 0.050 at~1.0 (February) and 0.470 at~0 (October), its screening EMR 0.974 and 0.990, yet more than half of the articles still received a different complete extraction across runs. The two executions are eight months apart (Section~\ref{sec:limitations}), so the contrast combines the temperature change with any provider-side change in between. Temperature zero does not remove the variation, and the lever is closing: the provider's documentation states that its newer models return an error when \texttt{temperature} is set to a non-default value,\footnote{\url{https://platform.claude.com/docs/en/about-claude/model-deprecations}, accessed 9~October~2026.} so on those models a practitioner can no longer request~0 at all.

\textbf{Finding 7: A model that returns probabilities instead of a sample still varies.}
The decision model (Section~\ref{sec:jev}) never samples text, yet its screening EMR (0.956) sits inside the range of the generative API stacks, and the probability it assigns to the same option for the same abstract moved between identical calls for most abstracts. Non-determinism is therefore not a by-product of sampling that a different output format removes; it reaches a stack that returns distributions as well. What the distribution adds is a signal the generative stacks do not provide: an abstract whose option probabilities move across runs is identifiable from the output itself; this study did not test whether routing such abstracts to a human reader improves screening.

\textbf{Finding 8: Reproducible is not the same as usable.}
The three local stacks reach $\emr{=}1.000$ on extraction while returning schema-conforming output on 38--43\% of calls (Section~\ref{sec:conformance}), and Mistral reproduces a degenerate screening rule perfectly (Finding~4). Reproducibility and usability are separable, cheap to measure together, and measured together in no study in Table~\ref{tab:comparison}.

\textbf{Finding 9: A run card can record a configuration that was not executed.}
In the Claude execution at~1.0, the client attached the \texttt{temperature} field only when the requested value exceeded zero, so a request for~0 was sent without it and ran at the API default, while the run cards recorded \texttt{temperature: 0.0} because the provenance records were built from the requested configuration; the call hash, computed over the same requested values, could not detect the omission either. A single conditional, invisible in the configuration table, the run card and the hash, detached the executed configuration from the declared one. Provenance that records what was requested cannot detect this; provenance that records what was transmitted can.

\subsection{Implications for Evidence Synthesis Practice}

\textbf{For systematic reviewers:}
If using cloud-based LLMs for screening or extraction, results from a single run should be treated as one sample from a distribution of possible outputs, not as a definitive answer.
Running multiple repetitions and reporting variation metrics should become standard practice, analogous to how human inter-rater reliability is routinely measured.
It is tempting to place the stacks' screening EMR of 0.94--0.99 next to the $\kappa{\geq}0.80$ target pre-specified for our human screeners and read the comparison as favourable, and we resist that reading for two reasons.
First, the quantities are not commensurable: EMR and inter-run Fleiss' $\kappa$ measure how consistently a \emph{single} rater reproduces itself across repetitions, whereas Cohen's $\kappa$ measures whether \emph{two different} raters reach the same conclusion. A system can be perfectly self-consistent and consistently wrong (Finding~4).
Second, on this same corpus our own two human raters reached $\kappa{=}0.529$ (95\%~CI \ci{0.383}{0.674}; Section~\ref{sec:corpus}), so the $0.80$ figure functions here as an aspirational guideline rather than as a measured property of human screening. The honest comparison is therefore not ``models versus the threshold'' but ``models and humans each measured, on different constructs, against a threshold that neither was shown to meet.''
Extraction EMR (0.15--0.47), by contrast, requires no such careful framing: it is below the 0.80 threshold under each of the constructs discussed above.

\textbf{For journal editors and reviewers:}
Papers reporting LLM-assisted evidence synthesis should be expected to disclose: (a)~the exact model version, (b)~all inference parameters, (c)~whether results were verified across multiple runs, and (d)~provenance information enabling independent replication.

\textbf{For tool developers:}
Open-weight models have already been scaled in this journal for regulatory information extraction in the hydropower domain \citep{yoon2026hydropower}; our result adds a property to that choice which cost and control arguments do not cover, since the local single-device arm is the only configuration here that returned bit-identical output across all ten runs.
The large difference in extraction EMR between local and cloud deployment suggests that deterministic local inference should be the default for reproducibility-critical applications.
Local inference on consumer hardware (Apple~M4, 24~GB RAM) cost \$0.26 total for 174~hours across three models, versus \$69.38 for 32~hours of API inference---a 266$\times$ advantage in total outlay. Normalised per hour of inference the gap is far wider still (\$0.0015/h local vs.\ \$2.14/h API, ${\approx}1{,}400\times$; the local figure counts electricity only, not hardware, and the API figure excludes Gemini, which ran on the provider's free tier), since the local stacks ran five times longer for that outlay. Either way the cost advantage compounds with the reproducibility benefit; workload and cost scenarios for a review team are in Supplementary Section~S25.
Where cloud APIs must be used, every reported output should come with its run-to-run variation; whether majority voting across runs restores a stable output was not measured here.

\subsection{Relationship to Prior Work}

Table~\ref{tab:comparison} compares this study with prior work.

Our screening flip rates (1.0\% for Claude, 3.0\% for GPT-4.1, 6.4\% for Gemini) point in the same direction as the accuracy variations reported by \citet{atil2024nondeterminism} on general benchmarks; the two quantities differ (flip rate here, accuracy variation there), so the agreement is in direction only.
Whole-output extraction changed far more often than the screening decision. The two EMRs are computed on different outputs and item sets, so the ratios below compare those outputs and do not measure how much the task itself amplifies non-determinism: Claude's non-match rate increased from 1.0\% to 53.0\% (53.0$\times$; ${\approx}88\times$ if its two failed screening calls are not counted as non-matches), GPT-4.1's from 3.0\% to 85.0\% (28.3$\times$), and Gemini's from 6.4\% to 80.0\% (12.5$\times$).

The comparison with \citet{jensen2025chatgpt} is particularly instructive.
Their reported 94.1\% inter-session reproducibility for ChatGPT-4o extraction appears to align with our API screening EMR (93.6--99.0\%), creating the impression that API-based extraction is reasonably stable.
However, their metric measures per-field agreement across 2~sessions, while our EMR measures whole-output identity across 10~runs.
When we apply our stricter metric, extraction reproducibility is 15.0--47.0\%. The two figures differ in metric, model, interface, corpus and number of runs, so their ratio is not attributable to the metric alone; our own field-level EMR (Supplementary Table~S29) isolates the metric effect on the same runs.
Per-field metrics miss the combinatorial explosion of variation: when 5~fields each have 97\% individual reproducibility, the probability that \emph{all} fields match simultaneously is only $0.97^5 = 0.859$---and this is before accounting for the variable-length effect estimate lists that drive most of our observed non-matches.

\citeauthor{gartlehner2024extraction}'s \citeyearpar{gartlehner2024extraction} replication accuracies of 95.0--96.9\% with Claude~2 were measured over two replications, each against human extraction, so they do not measure run-to-run agreement; a 10-run design with output hashing detects items that change in only 1--2 of 10~runs, which a 2-run comparison would usually miss.

\textbf{The meta-analytic propagation experiment} (Section~\ref{sec:metaprop}) provides the most direct evidence of downstream impact.
For Gemini, the number of usable effect estimates varied from 154 to 171 across runs---an 11.0\% swing in the evidence base feeding the pooled result.
For GPT-4.1 the swing was 2.3\% (176--180), and even the most stable API-served stack, Claude, showed a 1.0\% swing (195--197).
Across API-served stacks, 1--20\% of articles produced a different number of effect estimates depending on the run, meaning that \textbf{the composition of a meta-analysis is not fixed when an LLM extracts the data}.
Over the full corpus the pooled interval excluded RR${=}1$ in every run; because the pooled set mixes increments, lags, outcomes and effect measures, this describes the propagation instrument at this $k$, not the PM$_{2.5}$--respiratory association. The per-run count analysis pools every extracted estimate, several per article, under a fixed-effect model that treats them as independent, so its intervals are too narrow; the stability statement rests on the random-effects re-analysis in the Supplement, which pools one estimate per article ($k{=}39$--63) and, under both DerSimonian--Laird and Hartung--Knapp--Sidik--Jonkman variances, changes no full-corpus conclusion. Run dependence appears at small $k$ (Section~\ref{sec:metaprop}).

\subsection{Limitations}
\label{sec:limitations}

The results are bounded by the limitations below; for each we state what it prevents us from concluding.

\textbf{Timing of the Claude stack.}
The Claude stack was run on 8~October~2026, eight months after the other five stacks, on a snapshot that Anthropic had announced for retirement (deprecated 30~September~2026, retirement 30~November~2026).\footnote{\url{https://platform.claude.com/docs/en/about-claude/model-deprecations}, accessed 9~October~2026.} Provider-side changes to the serving stack in that window cannot be excluded, so differences between Claude and the other API stacks cannot be attributed to the provider alone, and the temperature contrast of Finding~6 cannot be read as a pure temperature effect.

\textbf{Stack sample.}
Six stacks---three local 7--9B models on one device, three proprietary API-served models---are not a sample of deployment practice. The local-versus-API contrast varies weights, infrastructure and serving layer together, and the one same-checkpoint comparison does not hold weight precision or the request payload constant. We therefore cannot attribute the gap to a specific serving component, nor claim that other hardware, other runtime versions or other API stacks behave the same way.

\textbf{Ten runs per condition.}
With $R{=}10$, a per-item non-match probability of 0.30 or higher is detected with $\geq$95\% power under a binomial model, while rarer instability (per-item $p{<}0.05$) is under-detected; the local EMR of 1.000 bounds the non-match rate at $\leq$0.6\% (screening) and $\leq$3\% (extraction) and does not exclude lower rates. EMR values here are not comparable with EMR computed over a different number of runs.

\textbf{No within-stack seed ablation.}
Our data show that a transmitted seed does not buy determinism (Finding~6) and do not estimate how much the seed contributes on its own; that estimate needs one stack run with and without the seed, which we did not execute.

\textbf{An agreement coefficient below its target.}
Two blinded raters working from a pre-registered protocol reached $\kappa{=}0.529$ (95\%~CI \ci{0.383}{0.674}) against a target of 0.80, and the shortfall is statistically decisive ($z{=}-3.65$).
The disagreement is located: it is directional (exact McNemar $p{=}2.2{\times}10^{-4}$), and 17 of the 19 asymmetric discordances turn on a single inclusion criterion whose original wording admitted two defensible readings; showing that the amended criterion repairs it requires a fresh independent sample.
This prevents us from interpreting sensitivity or certifying the reference standard; it does not affect EMR, which needs no reference. Because the reference excludes were sampled from clearly off-topic records, the specificities in Table~\ref{tab:screening} do not show how often a stack would include a near-miss study.

\textbf{Usability of the local outputs.}
The three local stacks reach $\emr{=}1.000$ on extraction while returning schema-conforming output on 38--43\% of calls. This paper therefore does not show that local stacks yield usable extractions.

\textbf{Provenance of the transmitted payload.}
The released harness hashes the declared configuration and records a transmitted value only for the Claude stack's temperature, so a field dropped from any other stack's request body would not be detected by the deposited records. In the same-checkpoint cloud arm, the per-call provider label reads \texttt{groq}, a fixed string left in its script; the run cards record the route actually used (OpenRouter to DeepInfra).

\textbf{Unlogged retries.}
Because unparseable first responses were re-requested and attempts were not logged, we cannot state how much this resampling raised parse success or lowered EMR for any stack.

\textbf{No structured-output modes.}
Every stack received prompt-level JSON instructions through its standard endpoint (Table~\ref{tab:models}); none used the providers' structured-output or tool-use modes, so we cannot say whether those modes change extraction EMR or schema conformance.

\textbf{Screening EMR covers the decision only.}
It ignores confidence scores and rationales, so it does not measure their variation; a full-output screening EMR could only be equal or lower.

\textbf{Corpus composition.}
Sixty per cent of the corpus comes from the rule's low-confidence stratum.
It would be tempting to read these flip rates as upper bounds for standard workloads, on the reasoning that a typical review contains fewer borderline cases. That reading does not survive inspection of the stratum: 260 of its 300 abstracts carry the maximum inclusion score of~5, the same score borne by every clear-include, and all 300 carry zero exclusion reasons. The stratum marks where the automated rule was unconfident, which is not the same as where a human reader would hesitate, and its composition sits closer to the include side than to a genuine borderline.
We therefore make no directional claim about how these rates transfer to other corpora. Whether a review with fewer such abstracts would flip less often is untested here, and the enrichment fraction is a property of our sampling frame rather than a calibrated difficulty setting.

\textbf{Snapshot validity.}
For the three API-served stacks, the infrastructure and intermediate-precision routines---GPU topology, batching policy, weight checkpoint version, internal post-training---are opaque to the client and may change silently. The main stacks ran within a 3-week window (February~11--March~2, 2026), the same-checkpoint cloud stack and the Gemini and GPT-4.1 fixed-slot runs in April~2026, and the Claude and Jev arms on 8~October~2026. Our API results describe the snapshots observed in those windows and cannot be extrapolated to later provider versions.

\textbf{Single corpus and domain.}
All measurements come from one 500-abstract corpus on PM$_{2.5}$ and respiratory hospitalization, a literature that reports effects in a small set of formats (RR or OR with 95\% CI, per 10~$\mu$g/m$^3$ or per interquartile range). We therefore cannot say whether the extraction EMR values or the screening-to-extraction contrast hold for less standardized environmental literatures, for other periods, or for other domains.

\textbf{Single local device.}
The local $\emr{=}1.000$ was obtained on one device (Apple~M4, 24~GB RAM, macOS Darwin~24.6.0, Ollama~v0.15.5; the Ollama version is taken from the experiment log, not from the run cards). We cannot claim that the same local stacks are deterministic on other hardware or runtime versions, nor that they reproduce these exact outputs there.

\textbf{Pre-registration disclosure.}
This study is partly pre-registered, and we state precisely which parts, because the distinction matters for how much weight each result can carry.
The core analyses (Sections~\ref{sec:fieldlevel}--\ref{sec:metaprop}) are exploratory: the choice of 10~repetitions, whole-output hash EMR, four semantic-tier definitions, and fixed-effect meta-analytic propagation were made during analysis design but without an Open Science Framework or AsPredicted submission.
The dual-human labeling validation is the exception and is \emph{formally} pre-registered: the protocol, the screening templates, and the agreement script were frozen as an OSF registration on 2026-05-12 (\url{https://doi.org/10.17605/OSF.IO/FGN3E}), two months before either label set was returned, and that registration pre-specified the $\kappa{\geq}0.80$ target together with the contingency followed in Section~\ref{sec:corpus} when the target was missed.
The fixed-slot, same-checkpoint and silver-external analyses, the Claude stack at temperature${=}$0 and the Jev arm are likewise not pre-registered.
Their results therefore describe this dataset and cannot be read as confirmatory tests of hypotheses fixed before data collection.

\subsection{Recommendations}
\label{sec:recommendations}

Practical strategies for reproducible geoscientific data analysis, which already list non-deterministic generative-AI output among the barriers, have been set out in this journal \citep{schlogl2026reproducibility}. The recommendations below are specific to LLM-mediated steps and add to that practice rather than replace it.

\begin{enumerate}
  \item \textbf{Run each LLM step repeatedly} and report EMR together with the number of runs, since EMR declines as runs are added (Section~\ref{sec:fixedslot}); ten runs detect a per-item non-match probability of 0.30 with $\geq$95\% power, and fewer runs detect less (Section~\ref{sec:limitations}).
  \item \textbf{Record the transmitted request payload} and its hash in the call record, not the requested configuration.
  \item \textbf{Report the deployment stack}---weights, provider, infrastructure, API layer and access dates---not only the model name.
  \item \textbf{Do not treat temperature zero or a seed as a reproducibility control}; verify by repetition.
  \item \textbf{Report schema conformance and accuracy alongside EMR.}
  \item \textbf{Prefer local single-device serving} for reproducibility-critical steps when capability permits, with hardware and software versions pinned.
  \item \textbf{Where a model returns probabilities}, report how far the probabilities move across runs.
\end{enumerate}

\section{Conclusion}

LLM steps entering environmental evidence pipelines do not inherit the re-execution guarantee that the rest of the modelling toolchain provides. Across 35{,}636 calls, local single-device stacks reproduced their outputs exactly, while API-served stacks at temperature zero returned an identical complete extraction for 15--47\% of articles. A model that reproduced exactly on a local stack varied across runs when served in the cloud, so a model name does not specify the experimental condition. A transmitted seed, a fixed-slot output shape and a decision model returning probabilities each left the variation in place; temperature zero did not remove it, and one provider now rejects non-default temperatures on its newer models. Reproducibility was also separate from usability: the perfectly reproducible local stacks returned schema-conforming extractions on 38--43\% of calls.

Frameworks that assess computational reproducibility process by process \citep{zhu2025geosimulation} need a per-process check for LLM-mediated steps. Whole-output EMR and schema conformance provide it, provided the call records store the transmitted payload rather than the requested one (Finding~9). Because per-vendor figures expire with each provider update, re-running the audit on a new provider snapshot is one command per stack.
